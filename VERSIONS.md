# Service versions

Per-service iteration log for the StarkillerBench Hotel Reservation app.
The repo evolves each service through numbered versions (v1 = shakedown,
v2+ = realistic iterations). This file is the changelog; SPEC.yaml under
each service is the current contract, and each version's tests live in
their own dedicated file so they can be reviewed, retained, or rolled
back in isolation.

**Audit gate.** A new version is not started until its SPEC.yaml diff +
its new test file have been reviewed by a human. Implementation is then
re-generated by the agent and verified against those tests.

**Test-file convention.** New functionality goes in a new test file:
`server_vN_test.go` for unit tests, `saga_vN_test.go` for integration
tests. Previous versions' test files are not modified.

## payment

### v1 — shakedown
- 4 RPCs: `Authorize`, `Capture`, `Void`, `Refund`
- In-memory `authorizations` map; per-auth state machine
  `authorized → captured | voided`
- Partial refunds with accumulated `refunded` counter
- Idempotency on Capture and Void (silent retry on same auth_id)
- Unit tests: `services/payment/internal/server/server_test.go`

### v2 — chaos & latency injection
- Reserved `payment_token` values trigger deterministic behavior:
  - `tok_decline` — `Authorize` returns `FailedPrecondition`; no auth_id
    is allocated
  - `tok_capture_fail` — `Authorize` succeeds; `Capture` against the
    resulting auth_id returns `FailedPrecondition`; the auth stays in
    `authorized` so `Void` compensation still succeeds
  - `tok_refund_fail` — `Authorize` and `Capture` succeed; every
    `Refund` against that auth_id returns `FailedPrecondition`
- Reserved pattern `tok_slow_<ms>` — `Authorize` sleeps for `<ms>`
  before responding (cap 60000); malformed suffix degrades silently to
  ordinary behavior
- State addition: `chaos_mode` field on each auth record
  (`"" | "capture_fail" | "refund_fail"`)
- Unit tests: `services/payment/internal/server/server_v2_test.go`
- Integration tests: `tests/integration/saga_v2_test.go`

## booking

### v1 — shakedown
- 3 RPCs: `CreateBooking`, `GetBooking`, `ListBookings`
- Saga: `inventory.Hold → payment.Authorize → payment.Capture →
  inventory.Commit`, with compensating actions on failure
- In-memory `bookings` and `idempotency` maps
- Unit tests: `services/booking/internal/server/server_test.go`

### v2 — _planned: Postgres-backed booking records, NATS-based saga steps_
Deferred.

## cancellation
